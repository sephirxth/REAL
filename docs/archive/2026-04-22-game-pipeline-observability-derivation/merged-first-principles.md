# 通用游戏 Pipeline 可观测性的必然最小架构

作者：Codex + Claude Code 融合稿  
日期：2026-04-22  
来源：
- `codex-first-principles.md`
- `claude-first-principles.md`

## 1. 核心问题陈述

问题：如何让自动开发 pipeline 在无人介入条件下，对通用游戏的代码变更做出可信的 `PASS / FAIL / UNKNOWN` 判断，并据此驱动下一轮迭代。

关键实体：
- 游戏运行时
- Pipeline / Agent
- Probe / Control 接口
- 观测证据
- 验收标准
- 历史状态与恢复点

优化目标：
- 在有限预算下实现可恢复、可解释、可复现的自动判断
- 尽量减少对具体游戏品类的耦合
- 让“判断能力”建立在运行时证据上，而不是人工推测上

## 2. 融合后的公理系统

A1 运行时不透明性：外部程序不能直接获得游戏内部语义状态，除非游戏显式暴露。  
类型：物理 / 经验

A2 游戏是时变系统：状态是时间、输入、随机性与历史路径的函数。  
类型：物理 / 定义

A3 验证必须基于因果对：判断一次变更，至少需要可比较的 baseline 与 result。  
类型：定义

A4 语义鸿沟存在：原始日志、内存布局、像素流本身不自动等于“游戏语义”。  
类型：定义

A5 有限预算：自动评估的时间、算力与人工注意力有限。  
类型：经验

A6 不可观测即不可验证：若某个维度不对 pipeline 可见，则涉及它的正确性无法自动判定。  
类型：定义

A7 目标公理：pipeline 必须在有限成本下，为每轮修改输出可信、可恢复、可执行的 verdict，并驱动后续迭代。  
类型：目标

## 3. 必要机制推导

### M1 可控探测接口

推导：A2 + A3 + A5  
若不能主动把游戏带到关键状态，pipeline 只能随机游玩或等待自然发生，预算不可控。

反证：若无此机制，pipeline 无法稳定验证“进入战斗”“完成撤退”“进入 dusk”等关键节点，违反 A7。

### M2 状态读取接口

推导：A1 + A3 + A6  
要比较 baseline/result，至少要获得结构化观测态。

反证：若无状态读取，只能依赖崩溃与 stdout，绝大多数语义错误无法自动识别，违反 A7。

### M3 状态写入/注入接口

推导：A2 + A3  
路径依赖意味着 baseline 必须可控，否则两次运行并不比较同一个问题。

反证：若无状态注入，每次测试起点不同，结论漂移，违反 A7。

### M4 语义事件流

推导：A2 + A4 + A5  
游戏正确性常常体现在“转移过程”，不是单个静态终态；必须用语义事件表示关键变化。

反证：若无事件流，只看几张快照会漏掉瞬时错误、错误恢复、阶段切换失败，违反 A7。

### M5 语义注册表 / Schema

推导：A1 + A4  
Pipeline 不能自己猜“哪个字段是 HP、哪个事件是撤退完成”，必须有先验语义映射。

反证：若无注册表，证据不可解释，自动判断退化为文本猜测，违反 A7。

### M6 时序锚定与关联 ID

推导：A2 + A3 + A6  
每条证据必须知道它属于哪次运行、哪个 probe、哪个版本、哪个时刻。

反证：若无 `run_id / probe_id / build_id / session_id`，日志、截图、状态无法归属，判断失真，违反 A7。

### M7 视觉证据通道

推导：A4 + A7  
玩家体验包含 UI、镜头、可见性、空间布局、渲染反馈等内容，纯结构化状态无法覆盖。

反证：若无视觉证据，pipeline 对大量玩家可见错误失明，违反 A7。

### M8 健康分层与 verdict 持久化

推导：A5 + A7  
自动系统必须知道失败属于 build、runtime、probe 还是 gameplay，并把 verdict 保存下来供下一轮使用。

反证：若无分层和持久 verdict，generator 会修错对象，恢复链断裂，违反 A7。

### M9 复现元组

推导：A2 + A5  
非确定性游戏必须保存 seed、配置、地图、端口、平台、版本等复现条件。

反证：若无复现元组，失败无法稳定重演，fix loop 失效，违反 A7。

## 4. 最简架构

### 组件集合

#### C1 Control Plane

职责：
- 发 probe
- 控制输入
- 定向跳转场景
- 请求 capture

实现机制：
- M1

#### C2 Semantic State Plane

职责：
- 暴露结构化状态
- 提供读写接口
- 承载语义注册表

实现机制：
- M2
- M3
- M5

#### C3 Timeline Plane

职责：
- 输出语义事件
- 给所有证据打关联 ID 与时间锚
- 维护 delta / transition

实现机制：
- M4
- M6
- M9

#### C4 Artifact Plane

职责：
- 输出截图或短片
- 与 probe 和 session 绑定
- 承载视觉层证据

实现机制：
- M7

#### C5 Verdict Plane

职责：
- 聚合证据
- 分层判定失败类型
- 持久化 `PASS / FAIL / UNKNOWN`
- 保存恢复状态与下一步建议

实现机制：
- M8

### 最小性证明

- 去掉 C1：无法主动验证关键路径。
- 去掉 C2：无法获得可解释状态。
- 去掉 C3：无法证明过程，只能看静态片段。
- 去掉 C4：无法覆盖玩家可见问题。
- 去掉 C5：无法闭环迭代。

因此五层是最小集。

### 充分性证明

这五层合起来，刚好覆盖：
- 驱动
- 读取
- 解释
- 视觉佐证
- 判定与恢复

所以足以满足 A7。

## 5. 通用游戏必须暴露的最小可观测内容

- `build_id`

- `scene`

- `acceptance_id`

- `runtime_ready`
- `input_ready`
- `capture_ready`

### 5.4 语义状态

- `phase / mode / substate`
- 玩家摘要
- 目标摘要
- 资源摘要
- 风险摘要
- 世界位置 / 拓扑摘要

## 6. 为什么“特殊日志 + 关键节点截图”必要但不充分

### 必要性

- 特殊日志提供语义事件与运行摘要，是自动判断的最低门槛。
- 关键节点截图提供视觉证据，覆盖 UI、镜头、可见性与布局。

没有这两者，pipeline 既看不懂，也看不见。

### 不充分性

仅靠日志 + 截图仍然缺少：

1. **状态写入能力**  
   没法构造可控 baseline。

2. **语义注册表**  
   Pipeline 仍然可能读到文本，但不知道字段与事件真正意味着什么。

3. **关联 ID 与时序锚点**  
   无法确定这张图、这条日志是否属于当前运行。

4. **分层健康与 verdict 持久化**  
   无法区分“探测失败”和“玩法失败”。

5. **复现元组**  
   失败无法稳定重演。

所以：

`日志 + 截图` 是必要子集；  
`Control + Semantic State + Timeline + Artifact + Verdict` 才是充分结构。

## 7. 关键假设

H1 游戏运行时允许被仪器化。  
风险：闭源、反篡改、平台限制。  
失败后果：整套方案无法部署。

H2 游戏语义可以被压缩为有限且稳定的 schema。  
风险：高维连续状态、强涌现系统。  
失败后果：可观测性永远不完备。

H3 少量 probe 足以覆盖关键验收路径。  
风险：系统过于开放或高度随机。  
失败后果：只能做统计验证，不能做单轮确定验证。

H4 视觉采样能够代表关键玩家体验。  
风险：问题依赖连续时序或短瞬态。  
失败后果：需要短视频而非单帧截图。

H5 时钟、日志、事件和输入通道可以稳定对齐。  
风险：多线程抖动、网络延迟、平台差异。  
失败后果：证据归属不稳，结论噪声上升。

### 依赖关系

```text
H1 -> H2 -> H3
H1 -> H5
H3 -> H4
```

## 8. 局限性声明

### 根本性限制

- 有限观测永远不能证明“游戏完全没有问题”。
- 高随机系统无法被单次 probe 完全覆盖。

### 条件性限制

- 当 H2 失败时，可观测性只能局部成立。
- 当 H5 失败时，同一错误可能难以复现。

### 实践性限制

- 语义事件设计需要玩法建模。
- 通用层越抽象，项目层定制越不可避免。
- 采样越完整，性能与存储成本越高。

## 9. 结论

对于通用游戏，支撑 pipeline 稳定运行的不是“更多测试脚本”，而是一个面向验收的 observability contract。

这份 contract 的必然最小架构是：

- Control Plane
- Semantic State Plane
- Timeline Plane
- Artifact Plane
- Verdict Plane

因此应区分三件事：

- 架构是必然的：这是逻辑结论。
- 实现是有条件的：依赖关键假设。
- 效果是待验证的：属于经验问题。

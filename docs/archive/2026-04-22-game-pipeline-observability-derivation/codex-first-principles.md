# 支撑通用游戏 Pipeline 运行的可观测性必要内容

作者：Codex  
日期：2026-04-22  
方法：第一性原理推导

## 1. 核心问题陈述

如何为“自动开发 pipeline 驱动的通用游戏”建立一套最小但充分的可观测性，使 pipeline 能在有限成本下自动判断 `PASS / FAIL / UNKNOWN`，并据此继续迭代。

### 关键实体

- 游戏运行时
- 自动开发 pipeline
- 控制接口
- 观测证据
- 验收标准
- 历史状态

### 优化目标

让 pipeline 能稳定地“驱动游戏、观察游戏、判断游戏、恢复迭代”，而不是依赖人工读日志猜结果。

## 2. 公理系统

A1 运行时公理：游戏行为是时序性的运行时状态转移，不是静态代码文本。  
类型：定义

A2 可判定性公理：pipeline 只能依据它拿到的证据做判断，不能依据“作者意图”做判断。  
类型：定义

A3 有限预算公理：自动评估的时间、算力、人工关注度都是有限的。  
类型：经验

A4 玩家体验公理：游戏验收最终落在玩家可见/可感的行为结果上，而不只是内部变量。  
类型：目标前的经验约束

A5 目标公理：pipeline 必须能在有限成本下，对每轮修改产出可恢复、可解释、可执行的 verdict。  
类型：目标

## 3. 必要条件推导

### 机制1 可控探测接口

推导：A1 + A3 + A5  
游戏是运行时状态机，而不是静态文本；预算有限时，pipeline 不可能通过随机游玩穷举验证，因此必须能主动把游戏带到关键状态。

反证：若无可控探测接口，pipeline 只能盲跑或依赖人工操作，无法稳定验证“出发、遭遇、撤退、进入下一阶段”等关键路径，违反 A5。

### 机制2 运行身份与关联

推导：A2 + A3  
证据必须知道“属于哪次运行、哪个 probe、哪个任务”，否则自动系统无法在有限成本下完成归因。

反证：若无 `run_id / probe_id / session_id`，日志与截图无法归属，证据不可判，违反 A2。

### 机制3 语义级事件

推导：A1 + A5  
仅有低层日志不足以支撑自动判断，必须暴露业务语义，例如“目标发现”“目标结算”“撤退完成”“阶段切换”。

反证：若只有“按键、坐标、对象创建”，pipeline 无法高效判断“目标完成、风险发生、撤退成功”，违反 A5。

### 机制4 时序快照与差分

推导：A1 + A4  
游戏正确性常常是“前后变化”，不是单帧静态真相；玩家体验依赖状态转移。

反证：若无 before/after 或 transition snapshot，就无法证明 loot、risk、phase 是否变化，违反 A4。

### 机制5 视觉证据通道

推导：A4 + A5  
玩家可见问题必须有视觉证据，纯日志不能覆盖 UI、布局、可见性、镜头、渲染异常。

反证：若无截图/视频帧，pipeline 对视觉回归失明，违反 A4。

### 机制6 健康分层

推导：A2 + A5  
必须区分 build/runtime/probe/gameplay 四类失败，否则修复对象会错位。

反证：若把所有失败混成一个 `FAIL`，generator 会修错对象，pipeline 不可稳定运行，违反 A5。

### 机制7 复现元组

推导：A1 + A3  
非确定性游戏必须记录 seed、配置、地图、端口、版本等复现条件，否则每次失败都可能是另一个世界。

反证：若无复现元组，失败不能稳定重演，fix loop 失效，违反 A5。

### 机制8 持久 verdict 与恢复状态

推导：A3 + A5  
pipeline 是多轮系统，不是一次性脚本，因此必须持久化结果与上下文。

反证：若无持久 verdict/state，下一轮不知道该修什么、从哪恢复，违反 A5。

## 4. 最简架构

### 架构组件

- Control Plane：发送 probe、驱动关键路径、接收 ack  
  实现机制：机制1

- Observability Plane：输出结构化语义事件、状态快照、差分、违例、复现元组  
  实现机制：机制2、3、4、6、7

- Artifact Plane：输出关键节点截图/短片，并与 probe 关联  
  实现机制：机制5

- Verdict Plane：把证据归并成 `PASS / FAIL / UNKNOWN`，并持久化恢复状态  
  实现机制：机制8

### 最小性证明

- 移除 Control Plane：无法定向测试。
- 移除 Observability Plane：运行时仍然黑箱。
- 移除 Artifact Plane：视觉体验不可验。
- 移除 Verdict Plane：无法闭环迭代。

### 充分性证明

四组件组合起来，完整覆盖“驱动、观察、解释、记忆”四个必要环节，因此足以支撑 pipeline 运行。

## 5. 必然的最小可观测内容

- `run_id`

- `build_ready`
- `runtime_ready`
- `input_ready`
- `probe_ack`

### 5.4 语义阶段

- `phase`
- `mode`
- `substate`

### 5.5 关键实体摘要

- 玩家状态
- 目标状态
- 资源状态
- 风险状态
- 位置与拓扑状态

- 开始

- `evidence_refs`
- `recommendation`

## 6. 必然性论证

“特殊日志 + 关键节点截图”是必要的，但本身不充分。

真正充分的条件是：

`可控探测 + 关联身份 + 语义事件 + 时序差分 + 视觉证据 + 分层健康 + 复现元组 + 持久 verdict`

缺少其中任一项，pipeline 就会分别陷入：

- 不会驱动
- 不会归因
- 不会理解
- 不会比较
- 不会看见
- 不会分诊
- 不会复现
- 不会恢复

因此这不是“更好的设计”，而是满足目标公理 A5 的必要结构。

## 7. 关键假设

H1 验收目标可以被拆成有限个可观察命题。  
风险：高层体验无法被分解。  
失败后果：pipeline 最多只能做 smoke check，无法自动判定完整玩法。

H2 游戏可以输出语义事件而不过度污染运行时。  
风险：埋点成本过高或破坏性能。  
失败后果：只能退回低层日志，判定质量显著下降。

H3 关键玩家体验可由少量 probe 覆盖。  
风险：系统过于开放，少量 probe 无代表性。  
失败后果：需要统计式评估而非单次评估。

H4 随机性可以被 seed、重试或统计方式约束。  
风险：世界生成或 AI 行为高度混沌。  
失败后果：复现性下降，fix loop 成本上升。

H5 截图采样足以代表关键视觉状态。  
风险：问题依赖连续动画、时序闪烁、输入边缘时刻。  
失败后果：需要视频片段而非单帧截图。

## 8. 局限性声明

### 根本性限制

- 任何 pipeline 都不能仅凭有限观测证明“游戏完全没有问题”。  
  来源：A3 + A4  
  表现：最多给出在当前 probe 集合下的高置信 verdict。

### 条件性限制

- 若 H1 失败，则高层体验无法转化为自动验收。  
- 若 H4 失败，则单轮 verdict 的稳定性下降。

### 实践性限制

- 语义事件设计需要产品建模，不是纯工具问题。
- 通用性越强，事件本体越抽象；项目特化仍然不可避免。

## 9. 结论

对通用游戏而言，支撑 pipeline 稳定运行的必然最小架构不是“测试脚本更多”，而是一个面向验收的 observability contract。

它至少包含四层：

- Control Plane
- Observability Plane
- Artifact Plane
- Verdict Plane

该架构是必然的：这是逻辑结论。  
其实现是有条件的：依赖上述关键假设。  
其效果是待验证的：属于经验问题，而不是逻辑问题。
